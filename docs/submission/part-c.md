# Part C: reliability and security

Each row names the mechanism, the choke point (the place where a bad value cannot be constructed, as opposed to a call site that merely avoids it), and the tests that pin it. Test names and file paths come from the invariant maps in the service specs (`docs/specs/identity.md`, `engagement-ingest.md`, `engagement-store.md`, `payments.md`). Test identifiers were checked to exist in the tree at the time of writing. Status words: Built, Partial, Next (see the architecture overview).

Two rules hold everywhere: financially relevant operations are keyed by a durable business id (`spin_id`, `reserve_id`, `external_event_id`), and the database refuses what the code must not do (unique constraints, `CHECK (amount >= 0)`, row-level security, exact role grants).

Limits of this table, stated plainly:

- Rate limiting is not built, so "retries" and "invalid events" cover correctness and recovery, not abuse throttling (Next).
- Rejected inbound events are answered with a code and logged; there is no rejection counter metric (Partial).
- The websocket delivers at most once and has no missed-event replay; the client resyncs over REST (Next).
- Balance reads are eventually consistent after a spin (the coin credit travels by event); money commands read Postgres.
- Reconciliation reports a mismatch (run record, CLI exit code 1) and never repairs it; there is no pager (Partial).

## Preventing probability manipulation and unauthorized spins

The reward is decided on the server and nothing the client sends can influence it.

1. **The client has no input to the draw.** The spin body is `{}` or `{credit_id}` and nothing else; any other field is 422 (`INV-SPIN-NO-CHOICE`). The segment index, weights and a "random" value are never accepted. The tenant and the player come only from the verified access token (`INV-SPIN-PRINCIPAL-ONLY`).
2. **The draw is deterministic and recomputable.** `segment = select(HMAC(server_seed[version], spin_id), reward table version)`. The seed lives on the server, is versioned, and the table version is stored with the spin, so an auditor can recompute any spin after a rotation (`INV-WHEEL-DETERMINISTIC`, `INV-SPIN-RECOMPUTE-AFTER-ROTATION`, `INV-SEED-BY-VERSION`). Over one million simulated spins, the observed distribution stays within 0.5 percentage points of the configured weights (`INV-WHEEL-DISTRIBUTION`).
3. **The table is validated and hidden.** Weights are integers, the total is capped, a bad table is rejected (`INV-WHEEL-WEIGHTS-SUM`, `-REJECTS-BAD-TABLE`). The public wheel view returns labels and order only, never weights; a service that leaks them produces a 500 and no body (`INV-WHEEL-PUBLIC-NO-WEIGHTS`).
4. **A spin needs a credit the player owns.** Credits are created only by the deposit rules engine from a verified, deduplicated deposit. One credit is consumed by one conditional `UPDATE` scoped to `user_id`; someone else's `credit_id` is 404 and leaves that credit unchanged (`INV-SPIN-OWNERSHIP`, `INV-SPIN-ONE-WINNER-DB`). Replaying a spin returns the stored result and never redraws (`INV-SPIN-REPLAY`).
5. **Coins are not the client's to move.** The spin response carries the reward only. Payments credits coins from the `spin.completed` event with the key `spin:<spin_id>`; there is no credit route at all (`INV-X1`: the POST route table of payments is pinned by a test over the real module). Operators cannot mint, and an acting (support) token is refused on every coin route (`INV-ACTBAN-1..9`, `INV-X5`).
6. **Operators change odds only through versioned, audited configuration.** A new table version applies to later spins; a spin already drawn keeps its version.

Not covered by this prototype: an independent RNG certification and a provably-fair commitment scheme (the seed hash published before play). Both are in the next steps of the root README.
